# big5-matrix 白話導讀

這份導讀寫給第一次接觸這個專案的人（包括面試時要講解它的你）。不需要先懂編碼理論，
看完應該能用自己的話說明：這個專案解決什麼問題、怎麼做、發現了什麼。

## 一、它解決什麼問題？

電腦只認得數字。要存「中」這個字，必須先約定「中」對應哪幾個位元組，這個約定叫做**編碼**。
台灣和香港以前普遍用 **Big5** 編碼：一個中文字用兩個位元組表示，例如「中」是 `A4 A4`。

問題是 Big5 從 1984 年訂出來之後，各家廠商（倚天、微軟、香港政府、瀏覽器標準組織……）陸續往空位
塞了自己的字，於是出現很多「方言」。今天的程式語言（Python、Java、Go、Node.js……）各自挑了一種
方言，而且常常都叫它「big5」。結果是：

> Python 用「big5」把俄文字母 Ё 存成 `C7 B3`，Go 用「big5」讀回來，變成日文的「シ」，而且沒有任何錯誤訊息。

這種「默默變字」對處理舊資料的工程師很危險。過去有人比較過各家的**對照表**（紙上資料），
但就我所知，沒有人把**今天實際在跑的程式**全部拿來、對每一個可能的位元組組合實測過。這個專案就是做這件事。

## 二、七個關鍵想法（附生活比喻）

### 1. 窮舉，而不是抽樣
Big5 一個字最多兩個位元組，所以所有可能的輸入只有 256 個單一位元組加 65,536 個雙位元組組合，
總共 65,792 種。我們全部測，一個都不漏。

> 比喻：要知道一台販賣機會不會吃錢，不是丟幾枚硬幣試試看，而是把每一種硬幣、每一種按鈕組合都試過一遍。

### 2. 轉接程式（adapter）＋同一種「行格式」
每種語言都有自己的寫法。我們幫每個語言寫一支很小的「轉接程式」，它從標準輸入讀一行題目
（例如 `d<TAB>A140` 意思是「請解碼 A1 40」），輸出一行答案（`3000`）。主程式（Python）只要會
說這一種格式，就能跟 12 種執行環境溝通。

> 比喻：聯合國同步口譯。每個國家的代表講自己的語言，但會議記錄只用一種語言寫。

### 3. 「取代模式」看錯誤的代價
遇到壞掉的資料，多數程式會用「�」（U+FFFD）代替，然後繼續。我們故意用這個模式，因為這樣才看得出
一個錯誤「吃掉」幾個位元組。例如 `A1 22`（`22` 是引號 `"`）：有的程式輸出「� "」，有的只輸出「�」，
引號不見了。這在資安上很重要：過濾器和解析器如果看到不同的文字，攻擊就可能從縫隙鑽進來。

> 比喻：郵差看到地址寫壞的信，有人只退回那一封，有人把下一封也一起退了。

### 4. 參考答案：把規格「抄成程式」
瀏覽器遵守的 WHATWG 編碼標準，用文字描述了 Big5 解碼的每一步。我們把它一步一步翻成約 60 行
Python，當作「標準答案」欄。為了確定沒抄錯，再拿兩個獨立的真實實作來比：Firefox 的 encoding_rs
（65,792 個案例全部一致）和 Chromium（只差 <!--n:fact.chromium.differs-->4<!--/n--> 個，而那幾個後來證實是 Chromium 的 bug）。

> 比喻：照著食譜做一道菜當基準，再拿兩家名店的同一道菜來比，三者一致才相信食譜理解正確。

### 5. 精簡又可驗證的資料
<!--n:impls.runs-->40<!--/n--> 個轉換器、每個近 20 萬題的答案，原本有 22 MB。因為題目順序固定，就不必每行重複題目，只存答案，
再用 gzip 壓縮，最後只剩 5.6 MB，每個檔案都小於 100 KB。每個檔案開頭寫明它屬於哪一份題目清單，
manifest 再記錄內容的 SHA-256 雜湊，任何竄改或錯位都會被發現。

> 比喻：考卷答案卡只填 A/B/C/D，不必把題目抄一遍；卡片上印著考卷版本號，拿錯版本會被立刻發現。

### 6. 版本鍵＋漂移檢查
程式語言會更新，行為可能改變。每個轉接程式回報「決定行為的版本」（例如 Go 的 x/text 模組版本）。
CI 每次會重跑：版本一樣而結果不一樣 → 一定有問題，測試失敗；版本變了而結果不一樣 → 這是新發現，
只回報、不算失敗。

> 比喻：每年用同一套題目測體能。同一個人兩次成績不同要查原因；換了新選手成績不同，那是值得記錄的變化。

### 7. 文件裡的數字都是「算」出來的
報告和 README 裡的每個數字，都夾在隱藏的 HTML 註解標記中，標記寫著這個數字對應 `summary.json`
的哪個欄位。執行 `python3 -m big5matrix report` 會自動更新；CI 會檢查文件和資料是否一致。
所以不會出現「文件寫 260，資料其實是 259」這種事。

> 比喻：財報裡的數字由會計系統直接帶入，不是手抄，所以不會抄錯。

### 8.（加分）網站直接讀原始資料
網站沒有自己的資料副本，它在瀏覽器裡直接下載並解壓 `data/` 裡的檔案，即時計算。為了確保網站的
JavaScript 和 Python 分析算出一樣的數字，有一個測試會在 Node 裡執行網站程式碼，逐項比對。

## 三、發現了什麼（挑重點講）

1. **名字不可信。** 同樣叫 `cp950`，在 Python 是微軟的表，在 Java 和 ICU 卻是 IBM 的表。
2. **Node.js 不是瀏覽器。** Node 的 `TextDecoder('big5')` 用的是 ICU 的 windows-950，跟瀏覽器標準差了 <!--n:fact.node.vs_whatwg-->6,253<!--/n--> 個位元組序列（這是已知問題，Node 有待審的修正）。
3. **macOS 的 iconv 有嚴重問題。** BIG5-HKSCS 編碼器連「中」都無法編碼；Big5 編碼器會把「‹」默默變成「<」、「„」變成「"」，而且回報「完全正確轉換」。這種行為可能被拿來繞過輸入檢查。
4. **Chromium 的 bug。** 香港增補字符集裡 4 個「字母＋聲調符號」的字，Chromium 解出來是控制字元加上半個 UTF-16 代理對（不合法的文字）。
5. **Go 沒照它引用的標準做。** 遇到無效的前導位元組時，Go 會吃掉後面的 ASCII 字母，標準規定要保留。
6. **Perl 會默默丟字。** 檔案最後如果剛好截斷在一個中文字中間，Perl 會直接丟掉，就算你要求「有錯就停」也一樣。

每個問題都在 `findings/` 有重現程式和實際輸出；本專案沒有替任何人回報，要不要回報由儲存庫擁有者決定。

## 五、面試可能被問的 10 個問題

**1. 一句話介紹這個專案？**
把 <!--n:impls.runtimes-->12<!--/n--> 種執行環境裡 <!--n:impls.runs-->40<!--/n--> 個 Big5 轉換器，對每一個可能的位元組組合和每一個相關字元實測，
公開所有不一致的地方，並找出幾個看起來是 bug 的問題。

**2. 為什麼「全部測」做得到？**
Big5 每個字最多兩個位元組，而且沒有狀態，所以 65,792 種輸入就涵蓋所有字元和所有出錯方式。
全部跑完只要約 13 秒。

**3. 不同語言的錯誤處理方式不一樣，怎麼比較？**
分成兩個問題分開比：「這幾個位元組是不是一個字、是哪個字」（所有實作和對照表都參與）；
「出錯時會吃掉幾個位元組」（只有真正執行的轉換器和 WHATWG 演算法參與，因為對照表沒有定義錯誤行為）。

**4. 你怎麼確定參考答案（WHATWG 欄）是對的？**
除了照規格寫的單元測試，還拿 Firefox 的 encoding_rs 比（全部一致）和 Chromium 比（只差 <!--n:fact.chromium.differs-->4<!--/n--> 個，經查是 Chromium 的 bug）。

**5. 你怎麼確定那些「bug」不是你的程式寫錯？**
每個結論都用第二種方法重新確認：直接用該語言的命令列工具（例如 `/usr/bin/iconv`）或幾行獨立程式碼，
不經過轉接程式，結果必須和資料一致。`tools/verify_claims.py` 自動做這件事。

**6. 資料怎麼存才能放進 git？**
題目順序固定，所以每行只存答案；用固定時間戳的 gzip 壓縮，讓每次產生的位元組都一樣；
manifest 記錄解壓後內容的雜湊，避免不同版本的 zlib 被誤判成資料改變。

**7. 程式語言更新了怎麼辦？**
每個轉接程式回報決定行為的版本。CI 重跑時，版本相同就必須完全一致，版本不同就只回報差異。

**8. 有遇到什麼困難？**
例如 ICU 有些轉換器出錯時會輸出 U+001A，但它也會把正常的位元組 0x7F 解成 U+001A，分不出來。
解法是在 ICU 的錯誤處理函式外面包一層，記下哪些輸出是錯誤替代字，再在格式裡標記成 `!001A`。

**9. 這對實務有什麼用？**
工程師搬移 Big5 資料前，可以在網站上查他要用的兩個程式（寫入端和讀取端）之間會不會掉字、
掉哪些字；報告最後也有具體建議，例如「指定轉換器而不是名稱」「不要依賴 U+FFFD 偵測錯誤」。

**10. 有什麼限制？**
沒有實際在 Windows 上跑（用微軟公開的對照表代替）；沒有測 Linux 常用的 glibc iconv；
Ruby 和 Perl 是 macOS 內建的舊版；只測一到兩個位元組長的輸入。這些都寫在 README 的限制一節。
